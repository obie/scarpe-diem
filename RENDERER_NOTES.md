# Scarpe native renderer: research notes (from source, 2026-10-01)

Citations are paths in ~/scarpe. Measured numbers from this machine are in DESIGN.md.

## Findings

**Q:** (1) What patterns do the reference apps use for high-performance animation (pre-create then move/style, pools, animate rates)?

Every app builds its shapes once and then only mutates them. (a) Pre-create and restyle: starfield makes 420 dots (plus 40 glows) at startup and each frame only sets left/top, and only when the rounded pixel changed (shown_x/shown_y cache). Marble Machine creates body+shine+7 tail ovals per marble on drop and then calls style(left:, top:). (b) Fixed object pools of hidden shapes reused forever: balloon_pop pools 90 confetti rects, 24 sparkle stars, 4 ring ovals, 4 string shapes and 4 'throw' stars, all created with hidden: true, then take(pool) picks a free entry (age nil or >= life) or steals the oldest; weather_window pools 24 ripple ovals with a round-robin index and 120 snow dots / 90-140 rain lines created once. (c) Dirty-checking: only touch a shape when its integer pixel or rounded value changed (starfield drift, balloon clouds `c[:art].style(left: x) if x != c[:shown]`, flowers `next if lean == f[:lean]`, sun rays `if reach != @ray_reach`); round floats to 1-2 decimals before sending (`.round(1)`). (d) Work lists instead of scanning everything: marble 'warm' pins list (@warm) so only glowing pins are recoloured and then dropped from the list; settled marbles skip draw (`return if marble.state == :settled && marble.path.empty?`); night_light twinkles only a rotating window of 1-3 stars per frame plus any with lit>0. (e) Variable rate per kind of motion: marble/starfield/typewriter/kanban use animate(60); balloon_pop/night_light/aquarium/weather use animate(30) and balloon_pop skips odd frames when idle (`next if n.odd? && calm?`); constellations twinkles at animate(12); pixel_pet animate(12); kaleidoscope animate(24) for spin; pomodoro animate(20) that stops itself (`@glide.stop if !@running && @shown == fraction_left`) and restarts with @glide.start. (f) The animate block receives a frame number; balloon_pop derives dt as (n - @last_frame)/FPS, starfield/marble use Time.now deltas clamped to 0.1 s. (g) z-order by layering: empty full-window stacks (@tails, @glass, @sky) are made at the right depth and shapes are append-ed into them later, so late-created shapes still draw under/over the right things. (h) Physics decoupled from render: marble runs 2 physics steps of 1/120 s per 60 fps frame.

**Q:** (2) How does marble_machine get hundreds of shapes moving at 60 fps? Key code.

It does not move hundreds at once. Hundreds of ovals EXIST (about 500 static pin ovals: 100 pins x 5 ovals each, plus 9 ovals per marble, so 64 marbles is roughly 576 more), but only the marbles currently rolling are restyled each frame, and settled marbles cost nothing. At the welcome pour of 24 and a 'Pour forty', one marble drops every 4 frames (`if @pour_clock % 4 == 0 ... drop_marble(...)`), so perhaps 15-25 are in flight at once (my estimate), each costing 9 style calls (body, shine, 7 tail dots) = ~200 style calls a frame. Key code: (1) creation once: `body = oval(x, y, RADIUS * 2, center: true, ..., fill: glass(color)); shine = oval(...)` and `tail = (0...TAIL).map { oval(x, y, tail_size(i), center: true, stroke: rgb(0,0,0,0), fill: rgb(*color, 0.3*(1-i/TAIL.to_f)**1.5)) }`, tails appended into a lower layer stack (@tails) than bodies (@glass). (2) per frame: `marble.body.style(left: x, top: y); marble.shine.style(left: x - 2, top: y - 2.5)` with x,y `.round(1)`; settled marbles `return if marble.state == :settled && marble.path.empty?`. (3) Tail is not 7 separate physics objects: `marble.path.unshift([x, y]); marble.path.pop if marble.path.size > 14` then draw_tail walks the 14-frame path placing dots every TAIL_GAP=4.5 px. (4) Physics is cheap: one pin lookup by arithmetic (`pin_near` computes row and column from y/x, 'the rows are too far apart for two'), marble-marble collisions by `sort_by!(&:y)` then an inner loop that `break if b.y - a.y >= RADIUS * 2` (sweep-and-prune), 2 steps of STEP = 1/120 per frame. (5) Pins glow via a `@warm` list: `cool_pins` only iterates warm pins, multiplies heat by 0.9 and sets `pin[:halo].fill = rgb(*color, 0.18*heat)` then `@warm.reject!` below 0.03. (6) Ripples are pooled growth rings removed after 24 frames. (7) The sspec asserts no leak: `assert_equal static_ovals, ovals.size`. Measured cost context: one style(left:, top:) call is 5.3-5.6 us after the 28 Sep 2026 fix (8.1-8.6 us before), so 1,000 style calls is about 5.4 ms of Ruby per frame.

**Q:** (3) How does balloon_pop do sound (afplay, caps, mute) and confetti?

SOUND: class Sounds (lines 56-172). Synthesis in pure Ruby, once per distinct sound: `@last_file = @files[name] ||= write(name, loudest(note ? send(voice, hz(note)) : send(voice)))` so each WAV is generated lazily on first play and cached by name (first play of each note pays the generation cost in-frame; precompute at startup to avoid that). RATE = 22_050 mono 16-bit; LOUDEST = 0.3 (peak normalised to 0.3 of full scale). Voices: marimba = sin(hz) + 0.25*sin(4hz)*exp(-18t), times exp(-6t), 4 ms attack `rise`, last 10 ms faded to avoid clicks; puff = low-pass-filtered noise (`soft += (noise - soft) * 0.25`) times exp(-60t); pop = mix(puff, marimba(hz, 0.03)); party = 7 marimba notes mixed. All notes are on a pentatonic scale (c5 d5 e5 g5 a5 c6) so any order sounds musical. WAV writer: `data = samples.map { |s| (s*32_767).round }.pack('s<*')` plus a 44-byte header packed with 'a4Va4a4VvvVVvva4V', written with File.binwrite into Dir.mktmpdir('balloon-pop') (removed in at_exit). Playback: `@player = Process.detach(spawn('afplay', @last_file, out: File::NULL, err: File::NULL))`, tracked in @playing. CAP: AT_ONCE = 6; `@playing.select!(&:alive?); return if @playing.size >= AT_ONCE`. MUTE: `attr_accessor :muted`, `return if muted` at the top of play; the speaker button toggles `@sounds.muted = !@sounds.muted` and swaps wave/cross shapes (hidden flags), plays a 'tick' on un-mute. No-afplay machines: `rescue SystemCallError` silently. The sspec traps afplay via SPEC_TRAP_FILE and asserts file names, WAV header bytes, peak <= 0.3*32767, 6-sound cap (by stubbing spawn) and that nothing plays while muted. CONFETTI: pooled, see pattern (b). burst(x,y,kind): 14 pieces from `take(@confetti)` with random angle, speed 120-300, initial vy -120 upward, spin -600..600 deg/s, life 1.0-1.5 s, colours cycling [deep, light, white, gold]; plus 6 sparkle stars flying radially at 160 px/s; plus a ring and a dropped string. shower(count:) re-uses the same 90-piece pool for sky confetti (life 3-4.5 s, vy capped 160). fly_bits per frame: vy += 420*dt, vx *= 0.97, sway `sin(age*4+turn)*30`, and a fake 3D tumble by squashing height: `flat = (1 + 5*Math.cos(bit.turn*PI/180).abs).round; art.style(left:, top:, height: flat)` (so no rotate needed, the rect just changes height). Sparkles fade by restyling `fill: rgb(255,255,240,fade.round(2))` and `outer:/inner:` radii each frame. Big numbers and trophy use spring()/ease_out() easing and `style(size:)` on paras.

**Q:** (4) How does constellations seed and draw a sky?

grow_sky uses one deterministic RNG: `seed = Random.new(SEED)` with SEED = 1609, so the sky is identical every run and saved constellations refer to bright stars by index. It builds three arrays from that RNG: @faint = 420 stars `[x, y, size 1.2-2.4, alpha 0.2-0.75]` uniform over W x (56..HORIZON=540); @milky = 300 tiny stars along a diagonal band `t = rand; spread = (rand+rand+rand-1.5)*70` (sum of 3 uniforms gives a bell-shaped scatter) at `[-40 + (W+80)*t + spread*0.4, 500 - 420*t + 40*sin(t*4) + spread]`; @bright = 64 stars chosen by rejection sampling (`until @bright.size == 64 ... next if @bright.any? { |bx,by| Math.hypot(bx-x, by-y) < 46 }`) with size 3.0-5.2. Drawing the sky page: `background '#02040c'..'#1a2556'`; the Milky Way haze is 56 big faint discs (`fill rgb(170,185,255,0.009)`, sizes 90-140, centred along the same curve) so no edge shows (very low alpha stacking); then the 300 milky ovals and 420 @twinklers ovals (`oval x, y, size, center: true, fill: rgb(225,232,255,alpha)`); then two empty full-window stack layers (@saved_layer, @draft_layer) for lines; then for each bright star a halo oval (size*5.5, alpha 0.04), an inner glow oval (size*2.8, alpha 0.1) and a white core, then hover ring, last ring, a meteor line, hills (bezier `shape` silhouettes), pines, observatory. Animation: `animate(12) { |frame| twinkle(frame) }`: each frame 5 random @twinklers get `fill = rgb(225,232,255, base_alpha * rand(0.3..1.0))`; every 3rd frame all inner glows breathe `rgb(200,215,255, 0.1 + 0.05*sin(frame/7.0 + i))` (note @glows holds only the inner-glow oval per star because `map` returns the block's last oval); a meteor is one line restyled over 10 frames (`frame % 80 == 40` spawns). Saved constellations are pairs of lines (a 7 px wide low-alpha glow line under a 1.6 px crisp line) in @saved_layer, redrawn with `@saved_layer.clear do ... end`; the focus pulse recolours those lines via `under.stroke = ...`. Persistence is JSON in ~/Library/Application Support/Constellations. Pages are `url '/' , :sky` etc. with `visit`.

**Q:** (5) Does any existing app already do 3D, raycasting, plasma, or per-frame recolouring of many shapes? What has already been shown off?

No example does 3D, projection, raycasting, plasma or polyhedra (a grep for raycast|3d|perspective|projection|plasma|polyhed|cube|wireframe|z-buffer across examples/native found nothing relevant; 'depth' hits are fish swim depth and 'cube' is only the RYB colour cube comment). The heaviest animated scenes so far: (a) bench/ovals.rb: 500 translucent ovals ALL moving every frame at animate(60), measured 60.0 fps, p50 frame 16.6 ms, Ruby ~3.9 ms/tick (57% GC) + Rust paint 5.3 ms at 2x, Ruby 25% CPU / Rust 41% CPU (PERF.md). (b) showcase/starfield.rb: 460 ovals (420 stars + 40 glows) with 3-layer parallax and mouse look at 60 fps, with an on-screen fps counter. (c) marble_machine: ~600-1000 ovals existing, ~200 style calls a frame. (d) weather_window: 140 rain lines restyled with 4 props each per frame at animate(30), 120 snow dots, ripples (drops count 90 sun... rain 90/140). (e) kaleidoscope: every stroke's shapes get `style(rotate: turn)` every frame at 24 fps (rotation of many shapes, using `transform :center`), mirrored copies are packed into ONE shape per stroke so a stroke is 4-6 shapes however many mirrors. (f) Per-frame recolouring is small everywhere: constellations 5 twinklers + 64 glows every 3rd frame at 12 fps; night_light 1-3 stars (+ lit) per frame at 30 fps; marble pins only warm ones; pomodoro 3 halo strokes; bubble_garden rainbow arcs fade-in. Nobody recolours ~1000 shapes every frame, nobody drives a computed per-cell colour grid, nobody does a depth sort, nobody draws strips whose height AND colour change every frame, and nobody records frames. Closest per-frame recolour benchmark in PERF.md is only 'recolouring one shape over 2000 paras' (1.45 ms to 0.32 ms per frame). Existing bench apps also test paint damage: scattered_damage.rb (12 dots) and turned_star.rb (rotated star colour change used to repaint the full window until 28 Sep 2026). So a 200-strip raycaster plus ~1000-cell plasma (~1,200+ changed shapes per frame, i.e. 2.4x the 500-oval bench) plus 3D polyhedra would be well past anything shown; budget estimate from PERF.md: Ruby handler ~9 ms and Rust paint ~12+ ms per frame at 2x, so 60 fps is marginal and 30 fps is the safe design target (my extrapolation, not measured). Damage tracking joins changes down to at most 8 rects (scattered_damage.rb comment), so a full-screen effect means a full repaint each frame.

**Q:** (6) What check (.sspec) patterns do they use for animation?

Format: YAML-ish front matter (`display: native`, `testability: interactive`, optional `timeout: 150`), a line `----------- app code` with `load File.join(Scarpe::Native::ROOT, 'examples/native/.../app.rb')`, then `----------- test code`. Patterns: (1) Deterministic randomness: `srand(7)` / `srand(6)` at the top so chance-driven animation repeats. (2) Reach into app state with `app = Shoes.APPS.first; state = ->(n){ app.instance_variable_get('@'+n) }` and assert on model objects (Marble structs, @balloons, pools). (3) Virtual time: `advance seconds` pumps animate/every/timer without sleeping (never `sleep`); marble uses `frames = ->(n){ n.times { advance 1/60.0 } }` and `frames.(60*6)` to let marbles land; balloon uses `advance 1`, `advance 40`. (4) Assert on motion: y decreases after `advance 1`; positions equal layout (`layout_of(shape).x` vs model x within 1.5, `layout_tree` boxes vs model for all 420 starfield stars with assert_in_delta). (5) Pixel truth: `pixel_at(x, y)` returns [r,g,b,a]; used with colour predicates (gold/cyan lambdas, `near` within 12 per channel) to prove the thing is actually painted; pomodoro checks arc colours at 6 o'clock and 1:30. (6) Leak checks: record `static_ovals = ovals.size` and assert equality after everything is removed (marble line 92); count 'flying' pool entries (balloon `bit.age && bit.age < bit.life`). (7) Input simulation: `click_at x,y`, `click_on proxy_or_text`, `press_key ' '`, `move_mouse`, and low-level `Scarpe::Native::DisplayService.instance.automation.mouse(:down|:move|:up, x, y)` for press-drag-release streams. (8) Invariant sweeps: pairwise non-overlap `settled.combination(2)` and bounds, bell-curve histogram assertion on piles. (9) Overriding methods for tests: `app.define_singleton_method(:close)`, stubbing `spawn` to count afplay launches, afplay is trapped by the runner (SPEC_TRAP_FILE lines listing the invoked commands). (10) fps text is only asserted by regex (`/\A\d+ fps\z/`). IMPORTANT harness gotchas: advance in small steps when many shapes move: 'One frame at a time: a single long advance of 460 moving shapes wedges the headless pipes' and pomodoro 'A second at a time: one long advance never reads what the display sends back, and a full pipe wedges it'. Also available: `snapshot(name)` writes spec/results/snapshots/<name>.png; `scarpe peek EXAMPLE --wait 1.5 --shot out.png`; headless runs with bundled fonts and `--scale 2` for Retina pixels. Run with `spec/run --display native spec/showcase`. Kids specs live in spec/kids/*.sspec, showcase in spec/showcase, legendary specs in each app's checks/ folder.

### Surprises
- A single Shoes oval costs about 5.3 us per style call and the whole 500-oval benchmark runs 60.0 fps with Ruby at 25% CPU and Rust at 41%; paint (tiny-skia antialiased fills, 5.3 ms at 2x) is the largest step, so ~1,200 changing shapes is roughly 2.4x that cost (my estimate, 60 fps marginal, 30 fps safe).
- The animate block yields a frame number n, and animate(240) on a 120 Hz display is paced to ~116 presents per second, so the frame counter and wall time can diverge; balloon_pop derives dt from (n - @last_frame)/FPS, which would be the exact way to make a frame-exact recording mode (advance by fixed dt per call).
- The spec harness already has an offline deterministic clock: `advance 1/60.0` pumps animate without sleeping, `snapshot(name)` writes a PNG of the headless frame, and `scarpe peek --shot` takes a still, so a frame-exact recording mode is feasible as a .sspec-style script that advances one frame, snapshots, repeats. Headless runs use `--scale 2` (Retina pixels) and bundled fonts. Gotcha: advance in single-frame steps when hundreds of shapes move or the headless pipe wedges.
- Rotation (style(rotate:)) of a shape used to repaint the whole window because rotated art had no paint bounds; fixed 28 Sep 2026 (turned_star bench: 150 full repaints down to 1 full + 149 partial, 5.6 ms to 0.12 ms a paint). Paint damage is merged down to at most eight rects, so many scattered changes are cheap but a full-screen effect repaints everything.
- Confetti 'tumble' uses no rotation at all: a rect's height is set to 1 + 5*|cos(turn)| each frame, a cheap fake 3D flip. This trick generalises to flat-shaded 3D faces (but a polyhedron face needs real polygons via shape).
- Kaleidoscope packs every mirrored copy of a path into ONE shape (`shape do ... end` with a loop of move_to/curve_to), so N copies cost one drawable; the same trick could batch many polygon faces or many raycaster strips as one `shape` per colour band, trading per-shape style calls for rebuilding the shape (rebuild cost not measured here).
- Hundreds of translucent ovals with very low alpha stack into a smooth haze: constellations draws the Milky Way as 56 discs at alpha 0.009.
- Sound is plain Ruby WAV synthesis plus afplay spawn; the apps cap concurrent afplay at 6 and the whole thing is trapped in the test runner. Pure-Ruby per-sample synthesis (Math.sin per sample) is slow for long tracks (balloon pop only makes 0.1-0.9 s sounds at 22,050 Hz mono, generated lazily on first use), so a multi-minute soundtrack should be generated ahead of time (or in a background thread/process before the show) and started with a single afplay at t0.
- Apps can have layers by creating empty full-window stacks first and appending shapes later; z-order follows creation order inside the slot.
- legendary apps ship zero fonts and rely on system font stacks; only the Kids set bundles Fredoka.ttf, which is loaded at runtime with font(path) and must be searched in four relative locations.

### Gotchas
- Slots and paras read a number between 0 and 1 (exclusive of 0, inclusive of 1) as a fraction of the parent, and a negative number as distance from the far edge; so a left/top of 0.5 means 50%. balloon_pop works around it with px(v) = (v > 0 && v <= 1) ? v.round : v.round(1). Anything moved to fractional positions near 0..1 must go through this, and anything that must leave the top of the window has to be a shape, not a stack (balloon_pop.rb:177-183, 294-299).
- A stack with margin gets its margins INSIDE the size you give it (pill buttons in marble/constellations use width+10 and margin [0,0,10,10]).
- Never advance the headless harness in one long step when hundreds of shapes move: single long advance wedges the headless pipes (spec/showcase/starfield.sspec:28, pomodoro.sspec:27-28). Step one frame at a time.
- Shapes are removed with .remove and leaks are detected by comparing ovals.size; hidden: true / .hide keeps a pooled shape cheap but it still exists.
- style(left:, top:) is slower in Ruby than the two setters left= / top= according to PERF.md:173-175, but move(x, y) sends two prop changes; style call cost is 5.3-5.6 us.
- Any rotate/scale/skew now has paint bounds (since 28 Sep 2026) but needs `transform :center` before creating the shape if rotating about its own centre (balloon_pop sun/trophy, kaleidoscope, marble none).
- The star() helper signature is star(x, y, points, outer, inner), arc takes radians with wedge: true for pie fills, line(x1,y1,x2,y2) with style(x2:, y2:) to move the far end, shape{move_to/line_to/curve_to} for polygons; transparent shapes use rgb(r,g,b,alpha) with alpha 0..1 and often `stroke: rgb(0,0,0,0)` or nostroke.
- Marble's comment: 'The card on the right counts the frames' - fps counter uses Time.now deltas over 30 frames and para.replace(strong(...)); pattern is reusable for a demo HUD (marble_machine.rb:418-426, starfield.rb:72-84).
- afplay is a separate process per sound, started with Process.detach(spawn(...)) so there is process spawn latency (tens of ms, not measured here) and no sample-accurate sync with frames; for a demo, start one long WAV at t0 and drive visuals from wall clock or a shared frame counter.
- The balloon sound generator computes samples lazily on first play inside the animate/click handler (balloon_pop.rb:81), which can hitch a frame; precompute all sounds before the first frame for a demo.
- qmd does not index this repo; use Read or Bash. Another process is compiling the renderer, so none of this was run; all numbers are from source and docs, estimates are marked.

**Q:** (1b) Transform methods and their exact semantics

rotate(deg): ADDS to a running total in the draw context (rotate 1 per frame spins; rotate nil drops the slot's own); positive = counter-clockwise (renderer applies -deg). Pivot is the shape's top-left corner (rect/oval/arc/shape), centre for star/arrow, or centre for anything after `transform :center` or with `center: true`. scale(x, y=x) sets outright (does NOT multiply; a Range picks a random value once); skew(x, y=0) sets outright, angles in degrees applied as tan(deg). translate(left, top) ADDS to a running total and moves shapes AND their layout boxes before they turn. transform(:center|:corner) picks the pivot, default :corner. cap(:curve|:rect|:project) = round/butt/square. All of them live in the slot's draw context and are inherited by child slots; clear keeps them. Per-object: `shape.style(rotate: 30, scale: [2,2], skew: [10,0], translate: [x,y], transform: :center)` works on any drawable after creation (draw-context keys are accepted by `style`). Applies to ART ONLY (rect oval arc arrow star line shape): text blocks, controls and slots ignore rotate/scale/skew. Images have their own `image.rotate(angle)` (rotate_angle prop) and `image.transform(:center)`; a turned image forces a whole-frame repaint.

**Q:** (5) Colour helpers, exact semantics, alpha

rgb(r,g,b,a=255), gray(level=128, alpha=255) [gray(0)=black, gray(1.0)=white, despite the manual's 'darkness'], named colours (red, cornflowerblue ... 140 CSS names; call with an alpha: red(0.2)), hex '#rgb' (nibble x17), '#rrggbb' in Lacci's to_rgb. Each component is typed INDIVIDUALLY: Integer = 0..255 (clamped), Float = 0.0..1.0 fraction (x255, rounded, clamped). So rgb(1,1,1) is black, rgb(1.0,1.0,1.0) is white, rgb(127.5,0,0) is full red (any Float >=1.0 clamps to 255), rgb(0,0,0,1) alpha is 1/255 (almost invisible), rgb(0,0,0,1.0) is opaque. Non-Float/Integer raises ('RGB values should be Float or Integer!'). Alpha is true opacity, composited straight (tiny-skia); fill red(0.2) over white is ~[255,204,204]. Result is a Shoes::Color < Array [r,g,b,a] with red/green/blue/alpha only (no dark?, invert, etc.). gradient(c1, c2, angle: 0) = two stops only, angle 0 = top to bottom, 90 = left to right; a Ruby Range of colours ('#fff'..'#000') is a gradient at angle 0; gradients stretch across the SHAPE's box, images tile. Strings that parse as colours are colours, anything else is an image path (png jpg jpeg gif bmp webp). Native itself also reads '#rrggbbaa', '#rgba', 'rgb(...)' and 'rgba(...)' strings, but Lacci's to_rgb raises on 5- or 9-character hex ('wrong number of digits') for styles routed through it. nofill/nostroke send an alpha-0 colour and mean 'paint nothing'.

**Q:** (6a) Surprise: a shape's path can be replaced every frame without rebuilding nodes (flat-shaded polyhedra, morphing blobs)

Shoes::Shape declares shape_commands as a style, and Drawable#style forwards any declared style as a prop_change. **Q:** (6b) Surprise: per-shape gradients, image fills and alpha make copper bars, glows and plasma cheap; masks make real clipping effects

**Q:** (6c) Surprise: a per-pixel framebuffer is possible through the image cache

Image files are decoded once and RE-READ when the file's modification time or length changes (checked once per batch); 'an app that rewrites a picture and sets its path again shows the new one, and a file that was not there yet shows once it is.' Formats png, jpg, gif, bmp (webp also recognised); up to 16,384 px a side. ### Surprises
- Positive rotate turns COUNTER-clockwise and ADDS to a running total in the slot's draw context (and survives clear), so `rotate 1` inside animate spins what it draws, but scale and skew SET outright and do not accumulate (spec/LEDGER.md:806-820; lacci/lib/shoes/draw_context.rb:71-135). translate also accumulates.
- A shape's path is a plain prop (`shape_commands`) that `style(shape_commands: [...])` can rewrite and re-render each frame, so flat-shaded 3D faces can be N pre-made polygon shapes whose vertices and fill are restyled per frame instead of rebuilt (lacci/lib/shoes/drawables/shape.rb:13-46, drawable.rb:565-590). Inferred from source, not run.
- `kerning` is true per-fragment letter spacing in pixels, and negative values pull glyphs outside the block box; spans can nest with different size/weight/stroke/rise, so rainbow sine-wave text can be built from ONE para of many spans with per-span `rise:` (px baseline lift) and `stroke:` colours (native/src/text/rich.rs:333-338, manual.md:1275-1286, 1366-1373).
- `mask { ... }` is real alpha clipping (backgrounds included, nests 4 deep, two frame-sized layers per level) and Hackety Hack's splash animates a rotating star inside one every frame (native/DESIGN.md:802-805, spec/LEDGER.md:820, native/src/limits.rs:22-23).
- Image files are re-decoded when their mtime or length changes and a file created later appears once it exists, which opens a software-framebuffer route (write a BMP, set `img.path`) for per-pixel plasma or tunnels (native/DESIGN.md:834-840). Unmeasured.
- Gradients and image patterns work as fill AND stroke on every art shape, and Ruby Ranges of colours are accepted directly (`fill: '#400'..'#f80'`); gradient angle 0 = top to bottom, 90 = left to right (spec/LEDGER.md:662-671, native/src/style/color.rs:89-133).
- Text cannot be rotated, scaled or skewed, and text colour is solid only (a gradient fill falls back to its first colour): any 'big rotating logo' must be art (shape/star) or an image, never a para (native/src/layout/mod.rs:638, paint/damage.rs:446, style/color.rs:76-85).
- Float vs Integer decides every colour channel and alpha: rgb(255*Math.sin(t), ...) with a Float is treated as a 0..1 fraction (clamps to 255), and an Integer alpha of 1 is 1/255, nearly invisible. Always `.to_i` computed channels, and pass alpha as a Float (0.5) or an Integer 0..255 deliberately (lacci/lib/shoes/colors.rb:260-266; FOR_AGENTS.md:286-287).
- Art stays in layout: `@dot.left/top` answer the numbers you gave (placed frame), while events, --layout and layout_of use window coordinates; transforms are reflected in layout boxes so hit-testing matches the turned picture (spec/LEDGER.md:781, FOR_AGENTS.md:422-424).
- Shoes 3 source (the lineage) turns every shape about its CENTRE by default but the manual and Scarpe say :corner; Scarpe keeps corner for rect/oval/arc/shape and centre for star/arrow only. Use `transform :center` or `center: true` for spin-in-place (spec/LEDGER.md:1688-1690, native/DESIGN.md:812-815).

### Gotchas
- rect heading in the manual says rect(top, left, ...) but the real order is left, top, width, height (ERRATA E3/M3: spec/LEDGER.md:727-736). oval's 3rd positional argument is a DIAMETER, while the `radius:` style is a true radius and doubles (E1: spec/LEDGER.md:705-715). Manual examples that call radius a width are wrong (M1).
- Per-shape `stroke: nil` does not remove an outline; use `nostroke`, `strokewidth: 0` or an alpha-0 colour. Unset fill and stroke default to BLACK with width 1, so every demo shape needs explicit pens (FOR_AGENTS.md:262-263, 275; D8).
- Pens apply to art drawn AFTER they are set. A shape block copies the canvas pens when its block finishes, so `stroke` set inside the block styles that shape, and the pen stays set for later shapes (spec/LEDGER.md:778-779). Lacci Shape is a slot, so pens set inside do not leak out (E7).
- Art inside `shape { }` is NOT individually coloured: the whole group is filled once (nonzero winding) with the shape's one fill and stroked once. The manual's Rules chapter claims such ovals are 'not filled'; Scarpe fills them (M21). Use one shape per colour.
- move_to/line_to/curve_to/arc_to are silently ignored outside a Shape block (lacci/lib/shoes/app.rb:585-651). arc_to is (cx, cy, w, h, a1, a2) with FULL w and h, centre-based, radians, unlike shape(left, top) which is a corner origin.
- arc() with unspecified wedge fills as a chord, not a pie; pass `wedge: true` (spec/LEDGER.md:832-841). Angles are radians (PI constants are provided), clockwise from 3 o'clock. star's first point is straight down; arrow points right and is centred.
- Float 0..1 for a position or size on art is PIXELS (C15 extended), but on every other element a Float between -1 and 1 is a share of the parent; a positional float on a slot, text or control makes things jump as it crosses fractions, so `.round` placed values (FOR_AGENTS.md:414-419; spec/LEDGER.md:587).
- scale and skew do not accumulate and 8-digit hex alpha ('#ff000080') is accepted by the renderer but Lacci's to_rgb raises on 5 and 9 character hex strings for styles it normalises (para stroke/fill); use rgb(r,g,b,a) or name(alpha) instead (lacci/lib/shoes/colors.rb:209-245).
- The window itself is a flow: art is always placed, never flowed, but text, images and slots flow unless given left/top/move. Text blocks have 4 px default margins (12 below), so rows of paras are 16 px apart; set `margin: 0` for tight demoscene text (spec/LEDGER.md:512-521; FOR_AGENTS.md:409-411).
- `animate` defaults to 10 fps; always pass 60 (or 30). `clear {}` keeps timers, `visit` stops them; do not leak every-frame redraws (FOR_AGENTS.md:439-440; spec/LEDGER.md:1263-1271). `timer(0)` runs once layout has caught up; `scroll_max` is stale until then.
- image(w, h) { ... } is a clipped child canvas drawn live each frame, not a baked bitmap, and its `blur`, `glow`, `shadow` calls are accepted but not drawn; rotating a file image forces a whole-frame repaint (native/DESIGN.md:830-833, 925-926).
- Many moving translucent shapes cost the most to paint, damage tracking joins down to 8 dirty rects then repaints the whole frame when more than half is dirty, and every moved or restyled-with-layout item sends its rect back to Ruby. Prefer `style(fill:)` (layout-free) and `move` for per-frame animation; avoid creating or removing nodes per frame (FOR_AGENTS.md:685-691; native/DESIGN.md:920-932, 842-848).
- The system font default is Arial in Shoes 3 and text is read as points at 96 dpi there, but native defaults to PIXELS (M14, Q12); use `font: '... 20px'` or `size:` for predictable metrics, and `SCARPE_NATIVE_ARGS='--fonts bundled'` for reproducible widths (spec/LEDGER.md:1521-1525; FOR_AGENTS.md:190-192).
- Manual says styles for margin arrays are [left, top, right, bottom], hide/show on art works, and `displace` does not move layout; `mouse` is [button, x, y] with button 1 held (lacci/lib/shoes/app.rb:541-544). No `dark?`/`invert` on Shoes::Color (spec/LEDGER.md:615).

**Q:** (1) After a peek --key step, have the keypress handler run and its drawable updates been applied and laid out before the next --shot captures?

Yes, fully sequenced. perform runs steps strictly in order: `@steps.each { |action, value| send("do_#{action}", value) }`. do_key calls automation.key, which is Automation#request(:key). That call (a) sends the req to Rust, (b) Rust's key_input emits a `keypress` event to Ruby BEFORE the reply (Child#request doc: 'Rust ... writes every event the req causes before the reply, so those events are in the inbox when this returns'), (c) Ruby then runs dispatch_caused_events = `pump.drain` (your keypress handler runs now, synchronously, Lacci prop_change/create messages are posted to the child outbox immediately) followed by `child.flush`. The next --shot is request(:snapshot). On the Rust side `Incoming::Req` does `self.flush()` (applies batch, lays out) before `handle_req`, and Snapshot calls `shown() -> picture() -> paint_into()` which itself calls `ensure_layout`. Headless Rust reads stdin batches and handles lines strictly in order. Handler exceptions are surfaced and fail the peek run (`peek: NameError: ...`, exit 1). Quoted sequencing code: peek.rb `@steps.each { |action, value| send("do_#{action}", value) }`; automation.rb `def request(op, **fields); reply = @service.child.request(op, timeout: REQUEST_TIMEOUT, **fields); dispatch_caused_events ...`; `def dispatch_caused_events; @service.surfacing_handler_errors { @service.pump.drain }; @service.child.flush; end`; runtime.rs `Incoming::Req { req, op } => { self.flush(); ... self.handle_req(req, op); ...}`. Caveat: the keypress only reaches the app via `subscriptions(app, "keypress")` (an app-level `keypress { |k| }`) and a focused edit_line/edit_box swallows plain chars (input.rs:1047-1074, send_keypress=false unless Escape or modified). `--key f` parses to a plain 'f' char (KeyInput::parse, input.rs:155-182) and the handler receives "f".

**Q:** (4) Do animate timers keep running in real time during peek when we do not --wait? Can they be suppressed?

No while steps run, with two exceptions. perform executes inside the pump's heartbeat handler (`Scarpe::Native.after_first_heartbeat { perform }`; dispatch_heartbeat calls the block from within Pump#step), so the pump loop is not turning while steps execute. Timers only fire from Pump#step (`@service.fire_timers`) or from Automation#advance. Automation#request/dispatch_caused_events never fire timers. So `--key`, `--click`, `--type`, `--shot` do not tick animate. Timers DO tick in real wall-clock time during (a) `--wait SECS` (do_wait -> automation.advance, non-frozen branch: `@service.pump.step while clock.now < deadline`) and (b) `--drag` (advance(DRAG_STEP=0.05) between points). Peek never freezes the clock: `spec_mode!` (which calls @clock.freeze!) is only called from the Shoes-Spec path, and nothing in peek.rb calls it, so peek has no virtual clock. Second exception: before the first heartbeat, the pump already ran its first step(s) (wait up to the next timer deadline, drain, fire_timers, then heartbeat), so an animate(30) created in the app body may fire 0 to a few real-time frames before peek's first step: nondeterministic. Suppression: no peek flag. Options: (i) app-side: detect recording with `ENV["SCARPE_NATIVE_HEADLESS"]` (exe/scarpe sets it to '1' for every peek) or your own env var, and in that mode never call animate/every/timer, or create the animate and `.stop` it immediately (Timers supports stopped; set_stopped on prop_change). (ii) Make the scene a pure function of a frame counter that your `keypress { |k| @t += 1.0/30 if k == 'f'; render }` handler advances; with no running timers each `--key f` is exactly one 1/30 s tick.

**Q:** (5) Is there a better built-in path: could a Shoes-Spec check drive a frozen clock and write a snapshot for every frame? Quote spec/README.md and the harness code.

Yes, and it is the only deterministic clock in the repo. spec/README.md (native API table): `| snapshot(name) | writes spec/results/snapshots/<name>.png, returns the path |` and `| wait_frames(n = 1), advance(seconds) | pump the loop; wait_frames also beats the heart, so a slot made since starts; advance fires timers |`; and 'Use `advance` for `animate`, `every` and `timer`; never `sleep`. Layout is deterministic because native runs headless with bundled fonts'. Harness code: shoes_spec.rb header 'the clock is frozen so timers move only on advance(seconds)'; `def snapshot(name); path = Automation.snapshot_path(name); automation.snapshot(path); path; end`; `def advance(seconds); automation.advance(seconds); end`. Under a frozen clock Automation#advance does: `target = clock.now + seconds; while (due = @service.timers.next_due_at) && due <= target + Timers::EPSILON; clock.travel_to(due); fire_timers; dispatch_caused_events; end; clock.travel_to(target)` then `wait_frames` (heartbeat + one headless repaint). snapshot_path: a name with no extension gets '.png'; an absolute path is used as is; else it goes under ENV["SCARPE_NATIVE_SNAPSHOT_DIR"] (default spec/results/snapshots); Automation#snapshot mkdir_p's the folder. You do NOT need spec/run or a .sspec: spec/support/suite/case_run.rb shows the mechanism, it just runs `ruby exe/scarpe --dev app.rb` with env SHOES_SPEC_TEST=<file of test code> (+ SCARPE_DISPLAY_SERVICE=native, SCARPE_NATIVE_HEADLESS=1, SCARPE_NATIVE_ARGS='--fonts bundled'). Lacci's App#initialize reads that file and calls run_shoes_spec_test_code, which calls spec_mode! (freezes the clock) and queues the test to run after the first heartbeat inside Minitest. So an arbitrary app file plus a 6-line test file gives a frame loop: `N.times { |i| snapshot(format('/abs/frames/%05d', i)); advance 1.0/30 }`. The test code runs in the same process as the app, so it can also call app methods or read ivars (the peekaboo_moles.sspec does `Shoes.APPS.first.instance_variable_get(...)`). Advantages over peek: no argv limit, no 12 KB shell line, a true frozen virtual clock so animate(30) frames and timers are exact, loops and per-frame logic in Ruby. Costs: each advance also does a headless `frames` repaint (Op::Frames paints once at the view scale), so each recorded frame paints twice (advance's wait_frames + the snapshot); and `snapshot(name)` takes no scale argument, so scale 2 must come from `SCARPE_NATIVE_ARGS='--scale 2'` (Options.scale is the default for headless canvases and snapshots). Float-drift caveat (inferred): clock.now is CLOCK_MONOTONIC (macOS uptime, often 1e5-1e6 s); repeated `target = now + 1/30` rounds at about 1e-10 per add, so over ~1000 frames the accumulated error can approach Timers::EPSILON (1e-9) and an animate deadline may slip one advance late and then fire twice in the next. If you want bit-exact frame counts, do not depend on animate under the spec clock: define `def render_frame(i)` in the app and call it from the test loop, or compare `frame` numbers in the animate block to spot a stutter.

### Surprises
- The frozen virtual clock is reachable for ANY app file without writing a .sspec or running spec/run: set SHOES_SPEC_TEST=<test code file> plus SCARPE_NATIVE_HEADLESS=1 and run `exe/scarpe --native app.rb`. Lacci's App#initialize (lacci/lib/shoes/app.rb:109-117) loads the test code, spec_mode! freezes the clock, and the test code runs in the same Ruby process as the app with full access to snapshot/advance/pixel_at and the app's ivars.
- peek does not freeze the clock and has no virtual time: --wait and --drag run the real pump in wall-clock time. Only Shoes-Spec mode freezes it.
- The test-code route makes the app a deterministic function of the loop: `advance 1.0/30` fires exactly the animate(30) deadlines in that span, in order, so recordings are bit-reproducible run to run.
- A synthetic --key / --click returns only after the handler ran AND its drawable messages were flushed to Rust, so `--key f --shot x.png` is a correct frame step with no sleeps (automation.rb dispatch_caused_events).
- Headless snapshots paint a brand-new Pixmap every time (`picture()`), never a damage-repaint of the window, so every shot is a full-scene paint: cost is scene complexity plus PNG encode, not an incremental diff.
- pixel_at(x, y) returns RGBA from the same offscreen paint, so the test loop can assert or checksum frames (for example detect a flat frame) without writing PNGs.
- Each snapshot costs two paints in the spec path because advance ends with wait_frames, which in headless mode paints a picture per frame count at the view scale before your snapshot paints again.
- The 1000 MP limit does not apply: MAX_PICTURE_PIXELS is 1<<26 (67 MP) and scales 0.1 to 8.0, so 3840x2160 (8.3 MP x 1) renders fine and even a 4K window at --scale 2 (33 MP) fits.

### Gotchas
- peek --scale N only changes the snapshot request's scale; the headless view scale for the extra `frames` repaints stays 1.0 unless SCARPE_NATIVE_ARGS='--scale N' is set. In the spec route, `snapshot(name)` has no scale arg, so you must use SCARPE_NATIVE_ARGS='--scale 2'.
- System fonts are the default for peek and for a bare headless run; spec/run adds `--fonts bundled` via SCARPE_NATIVE_ARGS. Set it yourself for reproducible text metrics (FOR_AGENTS.md notes widths differ).
- Peek has no stdin/file/@file step input; steps exist only in argv (macOS ARG_MAX 1,048,576 bytes incl. env, ~12k frame pairs).
- Animate timers may fire 0 to a few real-time frames before peek's first step (pump's first step fires due timers before the first heartbeat), so never derive frame index from animate under peek.
- Peek keypresses are swallowed by a focused edit_line/edit_box (input.rs send_keypress=false), and a focused button only reacts to Space/Return when keyboard focus is visible; keep the demo free of focusable controls.
- Float drift: Automation#advance under the frozen clock adds 1/30 to a CLOCK_MONOTONIC value (macOS uptime, ~1e5-1e6 s). Rounding error accumulates around 1e-10 per step and Timers::EPSILON is 1e-9, so a long run may shift an animate deadline by one advance. Drive frames by index (render_frame(i)) rather than by animate to avoid it.
- Handler exceptions during a step are surfaced by surfacing_handler_errors and abort the run (peek prints `peek: ...` and exits 1; a spec test errors), so one bad frame kills the render; there is no resume, so write frames to a stable directory and render in FIRST/LAST ranges.
- Rust request timeout is 30 s per request (Automation::REQUEST_TIMEOUT); a single frame that takes longer than that (huge canvas, slow disk) raises ChildTimeout.
- fakebin traps afplay, so under recording no audio plays or is captured; audio must be synthesized to a WAV offline and muxed by ffmpeg.
- PNG output is large (8.3 MB raw per 1920x1080 frame, compressed at zlib level 6 with no format/quality flag); expect GBs for 900+ frames and put frames outside the scarpe clone (peek's own note: PNGs lying beside an app get packaged with it).
- Do not run `scarpe peek` or the spec path until the renderer build finishes; the first run triggers `cargo build --release` in native/ (68 s, about 400 MB) and races with the other process compiling it.

**Q:** (2) What is the paint backend, and what do translucent shapes, gradients, text, images and large fills cost? Resolution scaling?

**Q:** (4) Are there batching APIs or fast paths (bulk move, style batching, dirty rects)?

There is no bulk-move or bulk-style API; every change is one NDJSON `props` line per drawable. What exists: (a) Per-frame batching on the wire: Ruby's pump does drain, timers, then ONE flush per step, which appends a `flush` line and writes the outbox in one write; Rust's reader hands every complete line in its 64 KB buffer to the event loop as one batch, applies everything, lays out and paints once per batch ('a frame of a thousand prop changes arrives once'). (b) move(l,t) and style(left:,top:) each emit one prop_change with all keys; `style` is heavier in Ruby than setters; move uses set_styles (validate_as per key). Setting just `left`/`top` separately sends two lines, so prefer move or style with both, and only send the coordinate that changed (starfield does this). (c) Dirty rects (damage.rs): each node is fingerprinted (box, clip, text, hover/focus, props-touched revision), changed nodes' old and new bounds become rects, merged down to at most 8 (nearest smallest-union-box first), and if the merged area exceeds 50% of the frame the whole frame repaints; each rect repaints into its own small pixmap with a 4 px margin. Whole-frame fallbacks: first frame, size/scale change, scrolling, popup/modal/tooltip, paint-order change, turned images. Past those, a few moving dots (12 scattered 8 px dots at 30 fps) cost 0.45 ms instead of 4.5 ms, but a scene where most shapes change is a full repaint. (d) Frame pacing: a frame that would be the third within two display refreshes waits, so floods are held to the refresh rate (120 Hz on this M5, unknown displays assumed 120 Hz) and a lone frame never waits. (e) Looks-only prop changes keep the layout (fill/stroke/cap on art, check, fraction, text on edit fields). (f) Art clipped to the window or off-screen is skipped (on_screen). Not done, by Nick's own notes: moving art without a full relayout, and a sprite cache for art.

**Q:** (7) How are animate frames scheduled, and what happens when a frame is slow?

Ruby's pump owns all timers (Rust has none). animate(fps) interval = 1/fps, minimum 1 ms; deadlines are origin + slot*interval. A timer that falls behind skips the missed deadlines instead of firing a burst, and the frame argument counts FIRES (0, 1, 2...), not elapsed time. So a slow handler gives fewer frames but no catch-up, and anything time-based (physics, scrolling, plasma phase) must read a monotonic clock, not frame*dt. One pump step = drain Rust messages, fire due timers, heartbeat, one flush. Multiple animate blocks due in the same step share one flush (one Rust frame). Default animate rate is 10 fps if none is given.

### Surprises
- Everything is CPU: tiny-skia software rasteriser into a Pixmap, copied to a softbuffer surface. On an M5 it still locks 500 moving translucent ovals at 60 fps using 41% of one core, because Ruby and Rust run as a two-process pipeline (Ruby 3.9 ms, Rust 6.7 ms per frame).
- Two OS processes talk over NDJSON on a pipe, and Rust batches every complete line in its buffer into one apply+layout+paint, so a frame of 1000 prop changes is one frame (43 KB write costs 0.03 ms; ping round trip 0.02 ms).
- Window frames go to CoreAnimation in DeviceRGB so the window server converts colour on the GPU; that one change cut present from about 2.8 ms to 0.78 ms per 1.2 MP frame.
- Dirty-rect repaint is verified bit for bit by SCARPE_NATIVE_DAMAGE=check over all 434 to 473 examples; SCARPE_NATIVE_DAMAGE=off gives a clean full-repaint baseline for A/B timing.
- Ghost windows (SCARPE_NATIVE_GHOST=1) are real, fully rendered, alpha-0 click-through windows that never take focus: ideal for a recording/benchmark run without disturbing the user.
- Lacci's layout push-back means Ruby gets told every rect that moved after each layout, so Ruby can read left/top/width/height of moving art, at a cost per moved shape per frame.
- Radial gradients, blur, glow and shadow on art are not drawn at all, and gradients are exactly two stops, so glow and copper-bar looks must be faked with many overlapping shapes or stacked 2-stop gradient rects.
- Nick's own starfield example tried a translucent nebula and dropped it at about 100 ms/frame; a 72-circle translucent nebula costs 58 ms per whole repaint at 2x, yet stars twinkling over it paint in 0.93 ms with partial repaint. Static expensive backdrops are fine as long as damage stays under 50 percent of the frame.
- The renderer sends machine-readable per-frame timings (parse, apply, layout, paint, present, per frame) for the last 10,000 frames in rust.json, so we can make a proof-of-performance panel in the recording from real data after the run.

### Gotchas
- Any prop change other than fill/stroke/cap on art (and a few control props) invalidates the layout of the WHOLE app, so every frame in which something moves costs layout over every node in the window (about 1.15 us per para-heavy node; 0.22-0.32 ms for 500 art nodes). Keep static text and widget counts low in a demo window and draw effects as art.
- No-op updates are not free: Lacci does not dedupe, Rust's Doc.set_props always returns true and touches the node's revision, so setting the same value still damages and repaints that node. Dedupe in Ruby the way starfield.rb does (only send the coordinate that changed, only when the rounded pixel changes).
- Damage falls back to a full repaint when the merged damage rects cover more than 50% of the frame or when over 8 rects cannot be merged small. A demo with most effects animating every frame is therefore a full repaint every frame, whose cost is the sum of all shapes at the window's physical resolution.
- Window pixel count is not adjustable: render scale equals window.scale_factor() (2x on Retina), so a 960x640 window is 2.4 MP. The full frame is also converted and presented on every frame regardless of damage. Pick the logical window size with the budget in mind (smaller logical window, fewer pixels).
- Large translucent overlapping shapes are the dominant cost (about 58 ms for 72 big translucent circles at 800x500@2x). Prefer many small shapes, opaque fills, or one pre-resampled image.
- Moving ANY node whose box is turned (rotate/scale/skew) is bounded by its turned box, and a rotated image always forces a whole-frame repaint; popups, modals, tooltips, scrolling slots and paint-order changes (z-order swaps, hide/show reorders, create/destroy) also force whole-frame repaints.
- animate frame argument counts fires, not time, and slow handlers skip deadlines rather than catch up; use a monotonic clock for time-based motion. A 60 Hz display caps presents at 60/s; the 120 Hz pacing allows up to 2 presents per 2 refreshes.
- All published numbers come from one M5 under load averages of 6-60. Heavy load pushed the 500-oval bench to 23 fps and paint to 10-13 ms, so measure before and after in the same session, and check `uptime` for load before trusting a run.
- Creating or clearing drawables is a Ruby-side cost (about 50-140 us per span, 93 ms to rebuild 200 ovals in the older FOR_AGENTS figure, GC 57% of Ruby CPU in the oval loop). Pre-create all shapes, never rebuild in the loop, use hide/show or off-screen parking for pooling particles.
- Stats files are written only on process exit and the frame log is capped at 10,000 rows; Ctrl-C paths may skip the write, so use --exit-after N for benchmark runs. Do not run the renderer while another process is compiling it; the dev binary is rebuilt when native/src changes.
- PERF.md describes move() as two prop messages; current Lacci move() sends one, so its Ruby/wire figures are from before that change. The sustained-count extrapolations (1200-1300 Rust-bound ovals, about 2000+ Ruby-bound moves at 60 fps) are my estimates, not measurements.

## Findings

**Q:** (1) Wire protocol Ruby<->Rust: message types, per-frame batching, diffing

NDJSON on the child's stdin/stdout, one JSON object per line, field t = type. Ruby->Rust: hello, create(id,kind,parent,index,widget,props), props(id,changes; explicit null unsets), destroy, reparent(id,parent,index), run, quit, focus, scroll_to, font, text_mode, flush, req(req,op,...) with ops dialog/layout/snapshot/click/mouse/type/key/wheel/resize/pixel/frames/focused/para_hit/para_caret/a11y/a11y_action/ping. Rust->Ruby: ready, event, mouse, para_hit, resize, scroll, layout (rects pushed back), closed, console, reply, log. Batching: Ruby buffers outgoing messages and writes on flush; the pump flushes once per pump iteration (after timers fire), so one animate tick = one batch; a req writes the buffer ahead of itself and Rust does an implicit flush before every req. Rust sets mid_batch=true for every message except Flush/Req/Hello and only asks for a redraw when the batch is complete; its stdin reader delivers lines in batches with one event-loop wake per batch. Diffing: there is no scene diff. Rust is retained-mode (Doc: id -> Node{kind,props,parent,children}); Ruby sends only changed props per drawable (props merge; unchanged props are not resent). Paint side diffs: partial repaint of only nodes whose box/props changed (damage.rs), and layout push-back to Ruby sends only rects that changed. Per-prop cost: one JSON line per drawable per changed set of props (500 moving ovals = 1001 lines, 43 KB, 0.23 ms JSON encode, 0.25+0.16 ms Rust parse+apply). Ruby never waits for Rust to paint: if Rust is behind, queued batches are applied together and one frame is painted (intermediate states are dropped). Timers live entirely in Ruby; Rust has no timer logic.

**Q:** (3) How is z-order decided and can it change?

Paint order is pure tree order (pre-order walk of the doc, creation order respecting index); there is no z-index/order prop. Backgrounds/borders are painted at their tree position too (a background declared first is under later siblings). Art is out of flow but still painted in tree order among siblings. A node moves in z only by reparenting: Lacci's drawable.set_parent(slot) removes it and re-adds it at the END of the children list, and the shim sends reparent{id,parent,index} (index nil = append), so set_parent(same_slot) = bring to front (public method, notify: true by default). Slot#before/after/prepend insert NEW children at a position, they do not move existing ones. A paint-order change forces a whole-frame repaint (partial repaint is disabled for that frame), which is irrelevant for a full-screen demo. Cheaper trick for painter's-algorithm 3D: keep a fixed pool of N shapes created in order and each frame write the i-th farthest face's shape_commands+fill into pool slot i, so nothing is reparented. hide/show (hidden prop) removes a node from layout and paint.

**Q:** (4) Transform support: rotate, transform :center, scale, translate, skew

Art only (plus Image rotate). Per-shape transform = rotate(deg, positive = COUNTER-clockwise) then scale [sx,sy] then skew [kx,ky] degrees (tan of radians), applied about the shape's top-left corner by default or about its centre when transform is 'center' (draw context) or the shape has center:true; Star and Arrow always pivot about left/top because that is their centre. A shape-block turns as one group about the group corner; members' own transforms are ignored. translate moves the art in pixels before turning. The effective value is the element's OWN prop first (style(rotate: 30) is absolute), else the creation-time draw context: slot-level rotate(n) and translate(x,y) ACCUMULATE as running totals in Lacci's draw context and only affect art created afterwards (a copy is taken at creation), so per-frame animation should set rotate/scale/skew via style on each existing shape, not call slot rotate. layout box, hit-testing and the pushed-back rects use the transformed bounding box. **Q:** (6) Clipping rules for slots and art

Only axis-aligned rectangular clips. (a) A slot with an explicit height (px, %, negative) clips all its descendants, art included, to the slot's full box (both axes); scroll: true with a height scrolls with an overlay scrollbar; scroll: true without height does nothing. A slot with only a width does not clip. (b) Image canvases (image(w,h){...}) clip their children to the image box. (c) The window clips everything. (d) Art has no clip of its own; art is not clipped by its slot unless the slot has a fixed height. (e) Clip rects nest by intersection. Clipped drawing uses one reused tiny-skia mask only for paths the clip actually cuts across; paths wholly inside or outside are drawn plain or skipped, so fixed-height slots are cheap. (f) A clipped slot's hidden part catches no pointer events. (g) Off-window art is culled before drawing (box grown by half its larger side + 8 px). (h) Non-rectangular clipping only via a mask slot: a slot holding a mask child paints its other contents through the alpha of the mask child's drawing, each masked slot allocating two frame-size layers per paint (nesting capped at 4). Backgrounds/borders ignore the parent's own clip (they use the clip of the slot's parent).

**Q:** (7) Frame clock, vsync, frame pacing, animate timing, how timers are driven

All timers (animate, every, timer) run in the RUBY pump, never in Rust. animate(fps) interval = 1/fps (default 10 fps, any positive Float accepted), frame number starts at 0 and increments per fire; deadlines are origin + slot*interval (no drift); a timer that fell behind skips missed deadlines (no catch-up burst) and fires at most once per pump iteration; the pump sleeps up to the next deadline (select on the child's stdout plus a wake pipe, max 1 s idle) and flushes once after firing. The animate block receives only the frame counter, no dt or timestamp, and no callback tells Ruby a frame was presented, so use Process.clock_gettime(CLOCK_MONOTONIC) for real time. Rust: ControlFlow::Wait, redraw requested only when the app's view is dirty and a batch is complete; present via softbuffer (CPU-rendered pixmap copied into a softbuffer buffer, not GPU, no vsync API), window colour space DeviceRGB so macOS composites on GPU. Pacing: Pacing::new(refresh_millihertz of the current monitor, else assume 120 Hz); a frame that would be the third within two refresh intervals waits until two intervals after the frame before last; a lone frame never waits. Effect: sustained output is capped near the display refresh rate (240 animate on 120 Hz gave 116 presents/s) but no real vsync alignment. Measured: 500 translucent ovals at animate(60) hold 60.0 fps (p50 16.6 ms, p95 about 19-21 ms, max about 28 ms), Rust paint 5.3 ms, Ruby handler 3.9-4.8 ms of which 57% is GC; YJIT cuts Ruby CPU about 13%. Heartbeat event every 50 ms. Idle app costs about 0% CPU. When Rust cannot keep up, queued batches are applied together and only the latest state is painted.

**Q:** (8b) Image canvases image(w,h){...}: can they be redrawn per frame? Are they offscreen?

An image canvas is NOT an offscreen raster. **Q:** Offline frame-exact recording: what the protocol offers

### Surprises
- Shape paths are fully mutable at runtime: shape.style(shape_commands: [...]) with move_to/line_to/curve_to/arc_to rebuilds the polygon each paint. Combined with a fixed pool of shapes and per-frame depth sorting by rewriting commands+fill into pool slot i, flat-shaded rotating 3D polyhedra need zero reparenting and zero create/destroy.
- A single prop_change can carry position, fill, rotate, scale and skew at once (style(left:, top:, fill:, rotate:)), one JSON line per sprite per frame, no validator cost. fill-only changes skip layout entirely (looks-only), so a 1000-rect plasma that only recolours is the cheapest possible workload (recolouring one shape over 2000 paras = 0.32 ms).
- Rust is a retained scene with partial repaints: it repaints only damaged rects, merges to at most 8 rects, and falls back to whole frame when more than 50% is damaged. A starfield of a few twinkling stars over a nebula painted in 0.93 ms in part vs 58.3 ms whole, so mixing a static backdrop with sparse motion is nearly free.
- Measured baseline: 500 translucent antialiased ovals at animate(60) in a window hold a flat 60.0 fps at 40-48% Rust CPU and 25-30% Ruby CPU (Ruby handler about 4 ms, 57% of it GC), Rust paint 5.3-5.9 ms at 2x. 1000 sprites per frame should fit in a 16.6 ms budget if kept to one style() call each.
- Rust offers real offline rendering: req snapshot paints the current doc to PNG at any scale 0.1-8 (up to 64 megapixels), callable from inside the app via display_service.automation.snapshot(path, scale:), so a frame-exact video export mode (render frame f, snapshot, ffmpeg) is possible, even at 4K+ scale.
- Frame pacing reads the real monitor refresh rate and assumes 120 Hz when unknown, allowing 2 frames per 2 refreshes, so animate(240) on a ProMotion Mac yields about 116 presents/s. Nothing enforces 60.
- Gradient angle semantics follow Shoes 3: 0 = top to bottom, 90 = left to right, any angle works for art fills, strokes, slot backgrounds and borders; alpha in either stop gives fade-out gradients. Image fill paths tile as a texture and are transformed with rotated art.
- Mask slots give non-rectangular alpha compositing (vignette/spotlight/iris wipes): contents are painted through the alpha of the mask child's drawing, at the cost of two frame-size layers per paint.
- A Rust animation can start with the window hidden and untouchable: SCARPE_NATIVE_GHOST=1 presents real frames to an invisible click-through window, useful for benchmarking a production without covering the screen; screen recording would need a visible window though.

### Gotchas
- No blend modes, no per-drawable opacity, no radial gradients, no glow/blur/shadow (stubs only). Faking additive glow means stacking translucent shapes; fading a whole effect means rewriting every colour's alpha.
- Shoes color alpha trap: rgb(r,g,b,1) with an Integer alpha is 1/255 (nearly invisible); use 1.0 Float or 255. Float channels scale by 255 per component.
- Positive rotate turns COUNTER-clockwise; default pivot is the shape's top-left corner except Star and Arrow (centre). Use style(transform: 'center') or center: true for centre pivots (and center: true also changes left/top to mean the centre). Slot-level rotate(n)/translate(x,y) are cumulative running totals and only affect shapes created afterwards.
- Oval strokewidth and radius are truncated to Integer by Lacci's validator (strokewidth 0.5 becomes 0, no stroke). Star outer/inner clamp negatives to 0. Use Rect or Star for fractional strokes, or bypass with style(strokewidth: 0.5), which skips validators.
- Only fill, stroke and cap changes on art skip layout. Anything else (left, top, x2, y2, angle, shape_commands, rotate) makes Rust relayout the whole app and push every moved rect back to Ruby as JSON, so unrelated paras or controls in the same window raise per-frame cost (about 1.2 ms of a 1.44 ms frame for a ball over 2000 paras). Keep the demo window's non-art content minimal or put effects in their own window.
- Layout push-back: every moved art rect is sent to Ruby each frame (contract a) and Ruby must parse it; 1000 moving rects means about 1000 extra entries Rust->Ruby per frame.
- Z-order is tree order only. Reparenting works via drawable.set_parent(slot) (moves to end) but triggers a whole-frame repaint. Sort by rewriting pool slots instead.
- Arc is a chord fill by default (wedge: true for a pie slice); angles in radians; a 2 < a1 wraps. Arc box semantics follow oval, not Shoes 3's centre.
- Star is centred on left/top and its first point points straight down; star box uses outer radius so an inner radius larger than outer overhangs and the layout box under-reports it (culling slack handles it).
- Shape commands have no close_path; fills close implicitly, strokes do not. Art inside a shape block is merged into one path (nonzero winding) and transformed as one group.
- Image canvases (image(w,h){...}) are live clipped containers, not offscreen bitmaps. There is no way to snapshot a sub-scene into a texture or reuse it; no crop/source-rect; both width and height stretch non-uniformly; images only load from files on disk (no data: URIs, only png/jpeg/gif first frame/bmp).
- A slot clips only if it has an explicit height; width alone does not clip. Art in an unclipped slot draws past it up to the window edge. Art is culled only when outside the window or clip.
- animate gives no dt or timestamp and no present callback; rendering is paced by Ruby's monotonic timer and Rust only reins in floods. Use Process.clock_gettime for time-based animation. Ruby handler time (about 4 ms per 500 sprites with Ruby 4.0 no YJIT, 57% GC) is the first limit; Rust paint (about 5.5 ms per 500 translucent ovals at 2x) is the second. Set GC tuning (e.g. GC.compact or reuse arrays) and RUBY_YJIT_ENABLE=1 (about 13% less Ruby CPU) in dev; packaged apps run Traveling Ruby 3.4.7 without YJIT.
- afplay and sound are out of the protocol entirely (Ruby side only); spec/support/fakebin traps afplay for safe test runs, so audio must not be run in agent tests.
- Headless peek/snapshot is deterministic only with --fonts bundled; the frozen Clock exists only for Shoes-Spec runs, so a frame-exact recorder must derive time from its own frame counter rather than animate wall-clock timing.
- DESIGN.md says this renderer is CPU softbuffer based (tiny-skia into a pixel buffer, copied on present at about 0.8-1.1 ms per 1200x1000 frame) with no GPU path; very large windows or scales multiply paint cost roughly linearly with pixels.

**Q:** (4b) Image from a file that changes on disk: cache invalidation

Yes, but only when a prop message prompts a re-read. ImageCache.get stats the file once per batch (the batch counter bumps on every flush) and keys on FileStamp {mtime, length}. **Q:** (5b) What happens between peek steps? Does a --key step pump timers or frames before the next --shot?

No. Rust does not paint or advance anything between requests. Headless serve() only handles lines as they arrive and paints only for a snapshot, pixel or frames request. Timers live entirely in Ruby (Rust has no timer logic). Peek.perform runs `frames(1)` once, then --size if given, then each step in command-line order. do_key calls automation.key, which sends one `key` req and then dispatch_caused_events (drain already-read messages and flush). It does NOT call pump.step, so no timers fire and no time passes. Only `--wait SECS` calls Automation#advance, which in peek (clock NOT frozen, since only spec_mode! freezes it) runs real pump.step loops for SECS of wall-clock time, so animate/every handlers fire at real deadlines. Then it dispatches events, sends a heartbeat and calls frames(1). Consequence: an animate(60) app is only advanced during --wait, the frame count reached by --shot is wall-clock dependent and non-deterministic, and the handlers run without any painting in between (cheap).

### Surprises
- Rust accepts ANY prop on ANY node and recomputes art geometry live every frame. Art style keys (rotate, scale, skew, translate, transform, cap, fill, stroke, strokewidth) are read from the node's own props first and draw_context second. So a plain `style(rotate: n)` on an art node animates rotation with no Lacci changes. A Shape's whole polygon can be swapped per frame by sending a new `shape_commands` array, which gives free-form flat-shaded 3D faces, vector-font text that CAN rotate, and a raycaster drawn as ~200 Rect strips, all as ordinary tree nodes.
- Text cannot rotate, but Shape paths can, so rotatable or 3D-projected lettering has to be drawn as stroked vector outlines.
- Image files are re-decoded when their mtime or length changes (checked once per flush batch), so a Ruby-side software renderer could write BMP or PNG frames to a file and re-show them via an Image node for true per-pixel effects. Costs: a synchronous decode on the render thread, a file write per frame, and Bicubic resampling to the drawn size, which is cached per size. A tiling image fill on art works the same way.
- Moving or reshaping art costs a full app re-layout (not just a repaint), but layout is cheap for art alone: 0.22 ms per 500 nodes. The measured paint cost is about 5-6 ms for 500 AA translucent ovals at 2x on an M5. That is the budget to plan around, roughly 10 us per small AA shape at 2x.
- --ghost gives a real presenting window that nobody can see or click, with no Dock icon and no focus steal. Useful for automated runs, and its snapshots read the Rust pixmap, not the screen.
- The Rust binary has a built-in stats recorder: SCARPE_NATIVE_STATS=<dir> writes rust.json with per-phase timings and per-frame rows. That is the way to get honest paint/layout/present numbers for the demo.
- Frame-exact recording is possible via an .sspec or a custom Ruby driver: freeze the clock with spec_mode!, advance(1.0/30), snapshot to numbered PNGs, then ffmpeg outside the app. There is no built-in recorder.
- The window shows frames through a CPU softbuffer copy at the physical resolution. There is no GPU anywhere. Performance is purely tiny-skia scanline fill rate plus the Ruby tick cost (3.9 ms per 500 moves, 57% GC).

### Gotchas
- Oval (and Arc, Arrow) left/top/width/height go through Lacci's convert_to_integer: Integer() truncation and negatives clamped to 0. An oval cannot go off the left or top edge or move sub-pixel. Use Rect with curve: width/2 for particles, or Star. Rect, Line and Star left/top are unvalidated.
- Peek does not advance time: --key and --click run no timers. Only `--wait SECS` runs the real loop (wall clock, non-deterministic frame count). A single peek cannot give a deterministic Nth frame. Use the frozen-clock sspec path with advance(1.0/fps) to do that.
- Headless/peek renders every snapshot as a fresh full-frame repaint at scale 1.0 unless --scale is passed to peek (only snapshots take it). Window mode paints at the display's physical resolution (2x on Retina, 4x the pixels), so peek screenshots at scale 1 understate window cost. Use --scale 2 for fidelity.
- Only fill, stroke and cap changes on art keep the layout. Every other art prop change relayouts the entire document. Animating a few paras (the sine scroller) re-shapes or re-lays-out the text each frame too, and large para counts get expensive (2000 paras = 38 ms layout).
- Damage tracking falls back to a full repaint when more than 50% of the frame changes, when paint order changes (reparent/index), when anything scrolls, when a popup/modal/tooltip is up, or when an Image has rotate_angle != 0 (bounds None). Full-screen effects will always be full-frame paints.
- Shape commands have no 'close'. Fill auto-closes but a stroke does not, so repeat the first point with line_to. arc_to takes (cx, cy, w, h, a1, a2) in radians. Shapes use nonzero winding, one fill and one stroke for the whole merged group, and the gradient bounding box is the union frame.
- Gradients are two-stop linear only. Anything fancier (radial, multi-stop, additive glow, blur, shadow, dashes) needs stacking many rects or ovals with alpha. There is no additive or screen blend mode, only SourceOver.
- Image reload needs a prod: Rust never watches the disk and only checks mtime+length when a layout or paint runs for that image in a new flush batch. Resend a prop (e.g. style(url:) with the same path) after rewriting the file. Write atomically (temp + rename). webp, tiff and svg are NOT decoded, only png, jpeg, gif (first frame) and bmp, though Ruby's shim happily passes .svg/.tif paths through (placeholder box results).
- The frame pacer holds frames to about the display's refresh rate (120 Hz fallback when unknown). Ruby's animate timer interval is 1/fps, the pump sleeps at most 0.05 s, and a missed deadline is skipped rather than bursting to catch up. So the real fps ceiling is min(Ruby tick rate, Rust paint rate, refresh rate).
- Docs say art under rotate/scale/skew/translate repaints everything (PERF.md:123-126), but the current code bounds transformed art in damage.rs paint_bounds (lines 441-447), so PERF.md is stale on that point.
- set_props marks pictures_to_check for url/icon/fill/stroke/draw_context, and unshown cached pictures are dropped at flush. A texture used only via a hidden node can be evicted and re-decoded.
- Outgoing `layout` rects are pushed to Ruby after layouts, so a frame-by-frame animation of many nodes also produces return traffic that Ruby must drain, which adds to Ruby-side cost.

**Q:** Q1. When Ruby calls drawable.move / style(fill:) / a setter, what is sent and when (immediate, batched, diffed)?

Lacci builds the change and fires a bus event immediately (synchronously). The native DisplayService normalises it and appends ONE NDJSON line {"t":"props","id":N,"props":{...}} to Child's in-memory outbox. Nothing hits the pipe until the pump ends its step (child.flush writes every queued line plus one {"t":"flush"} in a single write), or earlier if a blocking request is made (request writes the outbox at once; Rust flushes before any req). So it is batched per pump step, not per call and not per frame. There is no diffing on either side: Ruby always posts, and Rust's Props#merge just inserts, then marks the node touched and the view dirty. Re-setting an identical value still costs encode+parse+apply (+ possibly a repaint). move(x,y) is ONE message with both left and top (the 'two prop changes' line in native/PERF.md is stale; I printed the wire). Line#move is one message with left, top, x2, y2. Every single-prop setter (x2=, angle1=, points=, ...) is one message per call, so use style(a:, b:) to send several props in one line. Colours go through Normalize.color (hex/name/rgb/gradient to {"rgba":[r,g,b,a]} or {"gradient":[...],"angle":n}). Measured Ruby cost per call (M2 Ultra, Ruby 3.4.7 NO YJIT = packaged runtime, fake child that does the real JSON::State encode, load avg ~6): rect.move 7.7us, oval.move 7.9us, line.move 9.9us, oval.left= 4.8us, oval.width= 4.1us, style(left:,top:) 6.6us, style(fill:) 6.6us, rect.fill= 8.2us, style(left,top,width,height,fill) 13.2us, line.style(4 coords) 9.7us, arc.style(angle1,angle2) 7.8us, star.style(rotate:) 5.5us, para.text= 8.1us. Frame costs: 500 oval.move = 3.9 ms, 1000 rect.move = ~6-7 ms, 500 rect.style(left,top,fill) = 5.3 ms. **Q:** Q3. How do animate/every/timer get scheduled? What fps can animate reach, any cap?

Entirely by the Ruby pump on the main thread; Rust has no timer logic and sends no frame callbacks. Pump#step: wait for input (IO.select on Rust's stdout plus a wake pipe) for at most min(next timer deadline, 0.05 s; 1 s when idle), drain messages, fire due timers, send a heartbeat event at most every 50 ms, flush. animate(fps) makes a timer with interval 1/fps (default 10 fps; fps <= 0 or non-numeric falls back to 10); no minimum interval is applied to animate (every/timer are floored at 1 ms). Deadlines are origin + slot*interval (no drift). A timer that is late skips missed deadlines instead of bursting, and fires at most once per step, so the animate frame argument counts invocations, not wall time (use Process.clock_gettime deltas, as examples/native/showcase/starfield.rb does). Handlers run on the pump thread, so a slow handler delays input reads and later ticks. Practical cap: Ruby can tick as fast as the handler plus pipe allows, but Rust paces presents to the display refresh (a frame that would be the third within two refreshes waits; unknown displays assumed 120 Hz). **Q:** Q4. How do keypress/motion/click events reach Ruby, and what is the latency path?

Path: winit event in the Rust window loop -> Runtime::key_input / pointer_move / pointer_down -> out.event(...) writes an NDJSON {"t":"event","name":..,"target":subscription_id,"args":[..]} line on stdout -> Ruby's pump wakes from IO.select, read_nonblock(64 KB) -> JSON.parse -> inbox -> Pump#drain -> DisplayService#receive -> dispatch_from_child -> Shoes::DisplayService.dispatch_event -> your block (guarded: an exception is logged and the app continues). The handler's resulting props go back out at the end of that pump step. Repo-measured latency (ghost window, M-series): key in to the frame showing it 1.38 ms p50 / 1.87 p95; key, Ruby handler, form redrawn 2.78 / 3.29 ms (visible window earlier run: 3.8 / 7.9 ms). Details that matter: (1) Only key PRESS is forwarded (KeyboardInput with state Pressed); OS auto-repeat arrives as repeated presses; there is no key-up event, so 'held key' state must be emulated (macOS initial repeat delay is long). (2) keypress is not sent while an edit_line/edit_box has focus (except Escape and modified keys), nor for keys a focused control consumed. Cmd arrives as alt_ (:alt_q). Keys: printable = String, Return = "\n", others Symbols (:left, :escape, :f1); shift only folds into non-printables. (3) Every pointer move triggers a hit-test in Rust and a {"t":"mouse","state":[held,x,y]} message to Ruby, so App#mouse (polling [button,x,y]) is cheap and always current; motion blocks get (x, y, mods) only while the pointer is inside the parent slot, with no coalescing or throttling in Rust. (4) click/release: window coordinates (button 1/2/3, x, y); an app-level click block hears every press not consumed by a control/link. (5) wheel delta > 0 is up. (6) One handler per slot/app per event: a second keypress/motion/click block replaces the first.

**Q:** Q5. How does `scarpe peek` sequence steps? After --key, does it wait for a frame/redraw before the next --shot?

No frame wait after --key. Steps run in argv order inside one Peek#perform, started from the first heartbeat after the app is up (perform begins with automation.frames(1)). do_key -> Automation#key -> request(:key) -> Rust runs key_input synchronously and writes every event the key caused BEFORE its reply -> Ruby then runs dispatch_caused_events, which drains the inbox (your keypress handler runs now, inside the step) and flushes the handler's prop changes to Rust. The next --shot is a req snapshot: Rust flushes everything first (runtime.rs:251-252) then calls shown() -> picture(), which does a fresh synchronous full paint into a new Pixmap and saves the PNG. So the shot always includes the handler's immediate changes, independent of window presentation. What it does NOT include: anything a timer/animate would do, because peek pumps timers only during --wait or --drag. --wait SECS is real time (peek never freezes the clock; only Shoes-Spec calls spec_mode!): Automation#advance loops pump.step until the deadline, then wait_frames (dispatch events, heartbeat, then a frames request; in headless that paints n pictures synchronously, in a window it waits for presented frames). So peek animation is real-time and not frame-exact. Quotes: peek.rb: `def do_wait(seconds) automation.advance(seconds) end`, `def do_key(name) automation.key(name) end`, `def do_shot(path) shot = automation.snapshot(path, scale: @scale) || {}`; automation.rb: `def dispatch_caused_events; @service.surfacing_handler_errors { @service.pump.drain }; @service.child.flush; end` and in advance(): `deadline = clock.now + seconds; @service.pump.step while clock.now < deadline && @service.any_app_open?` then `wait_frames`.

**Q:** Q7a. Is there an API for creating many drawables cheaply?

No batch create, no instancing, no sprite cache (PERF.md lists 'A sprite cache for art' as looked at and left alone). **Q:** Q7b. Can an image canvas be redrawn, or can I push pixels?

There is no pixel-write API, no canvas redraw call and no bitmap message in the protocol (Incoming = hello, create, props, destroy, reparent, run, quit, focus, scroll_to, font, text_mode, flush, req). image(w, h) { ... } is a clipped container: the block runs with the Image as current slot and what it draws become the Image's children, laid out in image-local coordinates and clipped to its box. It is not a backing bitmap; you 'redraw' it by moving/restyling those child drawables. Image has children, contents, add_child, remove_child, destroy but no clear or append, so you cannot empty it in one call. Documented way to get changing pixels: rewrite an image FILE and set its path again. The renderer re-reads a picture when its mtime or length changes (checked once per batch), PNG/JPEG/GIF/BMP decode, and a picture shown at another size is resampled once and cached; pictures no drawable shows are freed at the next flush. So a software framebuffer is possible: write an uncompressed BMP (or PNG) to a scratch path each frame, then img.path = same path (one {"url": ...} prop). Cost is Ruby pixel generation (pure Ruby, no YJIT in a packaged app) plus a file write and a decode; use pack/String ops, not per-pixel loops, and keep the framebuffer small (e.g. 320x200) scaled up via width/height (inferred plausibility; not benchmarked end to end). Blur/glow/shadow on image canvases are no-ops.

### Surprises
- The app can drive its own deterministic offline renderer: spec_mode! freezes the clock, Automation#advance(dt) steps animate timers exactly, Automation#snapshot paints a fresh full frame synchronously (up to 8x scale, 64 MP) and writes a PNG. Headless needs no window and no screen recording; stitch with ffmpeg. All public Ruby calls, no renderer changes.
- Bypassing Lacci costs almost nothing to try: child.post(t: 'props', id: id, props: {...}) measured 0.41us per call against 7.4us for drawable.move (18x). A scene of 1000 shapes could update in well under 2 ms of Ruby per frame instead of 6-7 ms. The wire is plain JSON props; Rust never looks at Ruby's ivars.
- One Shape drawable can hold arbitrarily many sub-paths via repeated move_to. Bucket wall strips, stars or plasma cells by colour into a handful of shapes and replace each shape's shape_commands per frame (about 1.9us per command in Ruby). Cuts drawable count from 1000 to ~16.
- Rewriting an image file and setting its path again is a documented, supported reload (mtime/length check), so a small BMP/PNG written each frame behaves as a software framebuffer, composited by the Rust renderer, with scaling cached per size.
- Rust paces presents to the display refresh while Ruby keeps ticking: animate(240) on 120 Hz gave 116 presents/s; a flood never wastes paints. Rust also repaints only damaged rects (about 0.5 ms for a small moving thing over a busy still scene) and bounds turned/scaled art by its transformed box.
- App opacity is a live window-alpha style (fade the whole window in or out from Ruby).
- The renderer is cheap enough that Ruby is the bottleneck: 500 translucent ovals at 60 fps use 25-30% Ruby CPU and 41-48% Rust CPU; 57% of Ruby's time in that run is GC (stackprof in PERF.md).
- Pure-Ruby audio synthesis is quick enough to render a full track at startup: 2.45 M samples/s measured, so about 3 s for 3 minutes of 44.1 kHz mono.

### Gotchas
- Oval radius= after creation does nothing visible: Rust prefers width, and Lacci sent a width at creation. Change width and height.
- Oval/Arc/Arrow/Star left/top/width/height validators in the class files are dead (Drawable#validate_as finds the parent's no-validator entry first), so floats and negatives pass. Live validators: Oval radius and strokewidth (int, clamp >= 0), Arc angle1/angle2 (Float), Star points (int)/outer/inner (Float >= 0). style() bypasses all validation and width=/height= skip it too.
- Single-prop setters send one wire message each (line.x2= then y2= is two messages, arc angle1= then angle2= two, star three). Use style(...) to send several in one message. style(left:, top:, ...) with many keys costs more Ruby than two setters (13.2us for 5 keys).
- native/PERF.md still says move() sends two prop changes; the code sends one (drawable.rb set_styles). Ruby per-call numbers in PERF.md/style_cost.rb are M5, mine are M2 Ultra Ruby 3.4.7 no YJIT.
- No diffing anywhere: setting an unchanged value is still encoded, parsed, applied and marks the node touched. Guard in Ruby (starfield.rb only sends a coordinate when the rounded pixel changed).
- Any art change except fill/stroke/cap (position, size, x2/y2, angle, shape_commands, rotate) invalidates the whole layout, relayouts the document on the next flush and sends Ruby every rect that moved. Keep paras/controls out of the hot scene or few in number.
- animate's frame counter counts invocations, not time, and late ticks are dropped not replayed. Drive motion from a monotonic clock and dt (cap dt).
- animate defaults to 10 fps; give 60 (or 120 on ProMotion) explicitly. Rust presents at most about refresh rate regardless.
- Code after Shoes.app { } runs before the pump and window start. Handlers run on the one pump thread; a long handler blocks input reads and every other timer.
- timer(0) or any <1 ms timer with pending changes forces a blocking ping round trip to settle layout (and every timer(0) in a loop stalls frames).
- Shape has no close command, and add_shape_command outside the creating block re-sends the whole array per call (O(n^2)). Assign shape_commands once.
- Z-order is creation order within a slot; there is no z_index. set_parent(slot) re-appends to bring to front but sends a reparent plus relayout.
- Image canvases (image(w,h){}) are clipped containers, not bitmaps, and Image has no clear/append. Image#size needs fastimage (absent in --minimal builds).
- Keys: only presses (with OS auto-repeat), no key-up; no keypress while an edit field has focus; Cmd is alt_; shift only folds into non-printables. App-level keypress/click/motion blocks are one per event (a second replaces the first).
- peek: --key/--click/--type do not wait for a frame; they drain events and flush, then the next --shot does its own fresh full paint, so shots always show handler results but never timer-driven progress. --wait is real time (clock not frozen), so peek animation is not frame-exact. peek runs headless; use SCARPE_NATIVE_GHOST=1 for true frame rates.
- Packaged Ruby 3.4.7 has no YJIT, no encoding transcoders (String#encode between exotic encodings fails), no io/console, ripper, pty, objspace, rbconfig/sizeof, and no gems beyond vendored fastimage and base64. Develop and measure on the same Ruby (3.4.x, no YJIT) to avoid surprises; YJIT would otherwise cut 13-25% of Ruby frame time.
- GC.disable did not help in my 1000-move frame test (8.6 ms vs 5.9 ms with GC on); do not assume GC tuning is free, measure it with SCARPE_NATIVE_STATS.
- Snapshots and automation inside a real window: advance's trailing frames request waits for the paced presents (up to ~2 refreshes), so for offline recording prefer SCARPE_NATIVE_HEADLESS=1.
- afplay spawns are fire-and-forget (about 50-100 ms start latency is general macOS behaviour, unmeasured); sync audio to visuals by frame count with pre-rendered WAVs and start them from a keypress or timer, not from CPU-heavy Threads, which can stall the pump via the GVL.

**Q:** OPEN Q1 (3D polygons): Can a Shape's geometry be replaced per frame without remove/recreate, and what is the exact call?

Yes. Shoes::Shape declares `shoes_styles :left, :top, :shape_commands, :draw_context` plus stroke/fill/strokewidth, so `face.style(shape_commands: [["move_to",x0,y0],["line_to",x1,y1],["line_to",x2,y2]], fill: [r,g,b])` sends one props line. Rust rebuilds the path from the array at every layout and paint (geometry -> shape()). The box is path.bounds(), so it reports correct damage and layout rects. The only commands are move_to, line_to, curve_to and arc_to; unknown names are ignored and there is no close. Fill closes each sub-path implicitly. A shape made with no block starts with empty commands and draws nothing (PathBuilder.finish -> None) until commands arrive, so a pool of empty shapes is free to hold. Pens: a Shape with no stroke given falls back to the draw context and then to black 1 px (paint_art), so create the pool with `stroke: rgb(0,0,0,0)` or strokewidth: 0. Normalize.value walks the nested array once per element (no special colour handling for shape_commands).

**Q:** OPEN Q2 (raycaster/plasma): Which per-frame updates skip layout, and what does a typical mixed frame cost in Rust?

On art, only keys fill, stroke and cap are looks-only. A batch whose every key on a node is looks-only keeps view.layout, so a 1000-rect plasma that ONLY changes fill skips layout and push-back entirely. Any other key on any node in the app (left, top, width, height, x2, shape_commands, rotate, a para move) sets view.layout = None, and the WHOLE app relays out at the next flush. Art layout is cheap (out-of-flow, place_art per node; PERF.md measured 0.22-0.32 ms per 500 art nodes). So a frame that moves raycaster strips AND recolours plasma pays one layout over all nodes, then a full-frame paint (damage > 50%). Plan for paint as the cost: about 10 us per small AA translucent oval at 2x (5.3 ms/500); opaque axis-aligned rects come from PathBuilder::from_rect but have no published cost. A Rect with width or height 0 yields no path and paints nothing, so a strip can be 'hidden' by height 0 without toggling hidden.

**Q:** OPEN Q3 (sine scroller): Does moving a para per frame reshape its text?

Not when it is left-aligned and fits. A para with left/top is OutOfFlow and goes through place_positioned. width_for gives a positioned para its max-content width when that fits in the remaining slot width (`wanted <= fill`), else min(wanted, full); both are constant for a short letter, so the shape cache key (content + style + width) hits and the move costs layout plus a glyph blit. To be safe, give each letter para an explicit `width:`, which width_for returns directly. Positions on non-art elements MUST be Integers: a Float in (0,1] is a fraction of the parent and a Float in (-1,0) a negative share, so `.round` every computed left/top (JSON keeps 1.0 as a float). Text cannot rotate. Per-letter colour via stroke is solid only.

**Q:** OPEN Q4 (Ruby budget): Can the app bypass Lacci per update, and is the wire format safe to hand-write?

Yes, from public API. Scarpe::Native::DisplayService.instance.child is public (it would start the child, which already exists by then). Child#post(Hash) JSON-encodes into the outbox under a mutex, and the pump's flush sends it with the batch. The wire id is the drawable's linkable_id: prop_change posts `{t: "props", id: id, props: ...}` with the same id. Rust accepts any props on any node with no whitelist. Colours can be hand-written as [r,g,b] / [r,g,b,a] (Integer 0-255 or Float 0-1 per component), '#rrggbb(aa)', or {"rgba": [...]}. Costs of bypassing: Lacci ivars and the Ruby DisplayDrawable prop copy (display.update) go stale, and @layout_owed is not set. The only effect of that last one is that timer(0) does not settle. Ruby-side reader measured 0.41 us per raw post against about 7.4 us per move.

**Q:** OPEN Q5 (recording): What is the simplest frame-exact recorder, and does it need SHOES_SPEC_TEST/Minitest?

Neither is needed. Everything is public. (a) `Scarpe::Native.after_first_heartbeat { ... }` runs a block inside the pump once the app has drawn. (b) Inside it, loop: set every drawable for frame i from t = i/FPS (no animate), then `Scarpe::Native::DisplayService.instance.automation.snapshot('/abs/frames/%05d.png' % i, scale: 2)`. Child#request writes the whole outbox (your props) before the req. Rust flush()es before handle_req and paints a fresh full picture. Child#await reads stdout itself, so a blocking loop inside the heartbeat block works. Automation#request then drains and flushes events. (c) Afterwards do `Shoes.APPS.each(&:destroy)` the way the spec runner does. If you want to keep animate-driven code, call `DisplayService.instance.spec_mode!` (public; freezes the clock and turns dialogs off) and `automation.advance(1.0/FPS)` per frame, which fires exactly the due timers. That path paints twice per frame (advance ends with wait_frames -> frames(1)) and carries the float-drift risk against Timers::EPSILON. Each request has a 30 s timeout. Output is PNG only; the scale range is 0.1-8 and the picture limit 1<<26 px. Run with SCARPE_NATIVE_HEADLESS=1 and SCARPE_NATIVE_ARGS='--fonts bundled'. Per-frame PNG encode time has not been measured.

**Q:** OPEN Q6 (software framebuffer): If we write a BMP per frame and show it as an image, what does Rust do each frame?

On any batch where the file's mtime or length changed and a layout or paint asks for it, ImageCache.get re-decodes the file synchronously and replaces the entry with `sized: Vec::new()`. The cached resized copies are thrown away, so a picture shown at a size other than its own pixels is bicubic-resampled AGAIN on every frame (at_size; copies above 16 MP are drawn resampled on the fly). A 320x200 buffer shown at 1280x800 logical (2560x1600 device) means a decode plus a 4 MP bicubic resample every frame (unmeasured, probably several ms). Rust never watches the disk, so you must send a prop (img.path = same path) for it to look. Url is not looks-only on Image, so that also forces a relayout. A fixed-size BMP keeps the same length every frame, so the stamp depends on mtime alone; alternating two paths A/B removes the risk.

**Q:** OPEN Q7 (pooling): Does hide/show or shape pooling force whole-frame repaints?

No. same_order compares paint order only over nodes present in both frames, so nodes that appear or vanish (hidden toggles, new nodes) do not trip it. Reparenting or reordering kept nodes does, so set_parent-based z-sorting forces a full repaint. For painter's-algorithm 3D, keep a fixed pool of N face shapes in creation order and each frame write the i-th farthest face's commands and fill into pool slot i.

**Q:** VERDICT: Can a path/shape's geometry be updated per frame cheaply, and what is the cheapest way to draw an arbitrary moving triangle/quad?

Yes. `shape.style(shape_commands: [...], fill: c)` is the cheapest way to draw an arbitrary moving triangle or quad, and nothing else comes close. Rust side: one props line, a merge into the node's map, then a PathBuilder rebuild of a handful of segments during layout and paint. Layout is invalidated, but any moving art does that anyway, and an art-only relayout is sub-millisecond for hundreds of nodes. Ruby side: Normalize.value recursion plus JSON encode. The ruby-side reader measured about 1.9 us per command (122 us for a 64-point polygon), so a triangle costs roughly 8-15 us through Lacci (inferred). Rounding coordinates to 1 decimal or to Integers shrinks the JSON, and a raw child.post with a pre-rounded array costs less still. The alternatives lose. (1) remove plus recreate costs about 59 us of Ruby per create, plus destroy/unsubscribe work, plus a whole-frame repaint whenever order changes (avoid). (2) Rotated or skewed rects and transformed fixed triangles give affine images, but rotate/scale/skew are also non-looks-only props and decomposing a target triangle into Lacci's rotate·scale·skew-about-pivot order buys nothing over sending 3 points. (3) Line-based scanline fills cost one AA stroke per line per scanline, far more nodes. (4) Star/Arrow have fixed topology. Extra lever: one Shape can hold many sub-paths (repeated move_to), filled once with nonzero winding, so faces or strips of the SAME colour can share one drawable (bucket raycaster strips by shade). Caveats: AA fills of adjacent polygons leave faint seams on shared non-axis-aligned edges. That is inferred from tiny-skia's coverage AA; mitigate with a same-colour thin stroke or a dark underlay. Also give every pool shape an explicit transparent stroke, or each face gets a black 1 px outline.

### Surprises
- After the first heartbeat, an app can run a blocking frame loop (update drawables, then automation.snapshot) with no SHOES_SPEC_TEST, Minitest or frozen clock. Child#await reads Rust's stdout itself, and Rust flushes before every req, so each PNG holds exactly the state you just posted.
- Raw child.post(t: 'props', id: drawable.linkable_id, props: {...}) is a supported-looking path: DisplayService.instance.child is public, ids are Lacci's linkable_ids, and Rust takes [r,g,b] arrays and '#rrggbbaa' strings as colours directly.
- Paint-order checks ignore nodes that appear or vanish, so hiding and showing pooled shapes never forces a full repaint. Only reordering surviving nodes does.
- A Rect with width or height 0 paints nothing (no path), which gives a no-hide way to blank a raycaster strip.
- Positioned paras shrink to max-content width, so moving a single-letter para keeps its cached shaping. Per-letter paras in a sine scroller cost layout and a blit, with no reshaping.

### Gotchas
- native/PERF.md:171-173 is stale: move() sends ONE prop message (drawable.rb:663-690). PERF.md's claim that turned art repaints everything is also stale (damage.rs:428-449).
- Oval/Arc/Arrow position and size validators are dead (drawable.rb:63-75 detect finds Drawable's entry at :307 first), so floats and negatives pass. Oval radius= after creation does nothing (shapes.rs:109-111).
- Non-art positions and sizes: a Float in (0,1] is a FRACTION of the parent (dim.rs:52-67), and JSON keeps 1.0 a float. Always .round para left/top. Art coordinates are plain pixels (shapes.rs:68-80).
- A Shape with no stroke given strokes black 1 px by default (shapes.rs:409-411). Pass stroke: rgb(0,0,0,0) or strokewidth: 0 on every pooled face or strip.
- Rewriting an image file wipes its resized copies (image.rs:70-71), so a scaled-up software framebuffer pays a decode plus a full bicubic resample every frame. Show it at native pixel size, or accept that cost.
- A single non-looks-only change anywhere in the app (even one para moving) relayouts every node. Keep the demo window art-heavy and text-light. Only art fill/stroke/cap skip layout (runtime.rs:663-676).
- Recording via spec_mode! + advance paints twice per frame (wait_frames -> frames(1), automation.rb:120-150). Driving frames by index and calling snapshot directly paints once.
- Automation requests time out after 30 s (automation.rb:19), and a handler error aborts the loop. Render in FIRST/LAST ranges to a stable directory.
- Painter's-algorithm z-sorting through set_parent reorders kept nodes and forces Repaint::Everything (damage.rs:296-303). Rewrite fixed pool slots instead.
